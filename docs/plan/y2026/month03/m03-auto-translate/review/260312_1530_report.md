## Major Issues (P1 — Must Fix Before Merge)

### P1-1: Cloud path needs independent quota check

**File:** `src/2_background/handlers/AutoCandidatesRequestHandler.ts`

**Problem:** The existing manual translation flow checks `quotaManager.checkTranslationQuota()` before API calls and increments after success. The new `AutoCandidatesRequestHandler` calls the cloud API without any quota check.

**Decision:** Auto-translation should consume an **independent quota** separate from manual translation. The rationale:
- Auto-translation is supplementary — it should not eat into the user's manual translation allowance
- Auto-translation frequency is already bounded by the scan-once-per-block rule
- An independent daily quota (e.g., 50 auto-scan requests/day for free tier) provides cost control without reducing the manual translation budget

**Action Required:**
1. Design an independent quota counter for auto-candidates requests
2. Add quota check before cloud API call
3. Add quota increment after successful response
4. Return gracefully (empty candidates + `degraded: true`) when quota exhausted

**Priority:** P1 — Required before production release

---

### P1-2: `isAutoTranslation` flag defined but never set

**File:** `src/1_content/ui/translationDisplayV2/types.ts`, `src/1_content/services/autoTranslationService.ts`

**Problem:** The `isAutoTranslation?: boolean` flag was added to `TranslationEntry`, but `renderAutoCandidate()` calls `showTranslationResult()` without any mechanism to propagate this flag. Auto-translation entries in `activeTranslations` are indistinguishable from manual ones in the data model. The `--auto` CSS class is the only differentiator, but it's DOM-only — not queryable from code.

**Impact:**
- Cannot programmatically distinguish auto vs manual translations (future features: analytics, selective cleanup, "hide auto-translations" toggle)
- No way to count auto-translations per block accurately from the data model
- If CSS class is lost (e.g., tooltip re-render), the visual distinction is lost

**Suggested Fix:** Either:
- (a) Add an `isAutoTranslation` parameter to `showTranslationResult()` and propagate to `TranslationEntry`, or
- (b) Expose a method `setTranslationEntryFlag(id, flag)` on `translationDisplayV2`

**Priority:** P1 — Important for data model correctness and future extensibility

---

### P1-3: CSS opacity animation competition may cause visual flicker

**File:** `src/1_content/resources/content.css`

**Problem:** `showTranslationResult()` adds the `visible` class via a 10ms `setTimeout`, transitioning to `opacity: 0.8`. The `--auto` class is applied synchronously before that timeout fires, triggering the `ai-translator-auto-fade-in` animation immediately. When `visible` is later added, two competing opacity transitions run simultaneously — potentially causing a visual stutter.

**Suggested Fix:** Remove the standalone animation from `.ai-translator-tooltip--auto` and rely solely on the existing `visible` class mechanism:
```css
/* Remove the animation property from .ai-translator-tooltip--auto */
.ai-translator-tooltip--auto.visible {
    opacity: 0.6;
    border-bottom-color: #2A9D8F;
}
```

**Priority:** P1 — Affects user-visible rendering quality

## Medium Issues (P2 — Fix in This PR or Follow-Up)

### P2-4: AutoCandidatesGenerationService creates new instance per request

**File:** `src/8_generate/services/AutoCandidatesGenerationService.ts`

**Problem:** `generateAutoCandidates()` creates a new service instance and calls `initialize()` (loads prompts from resources) on every invocation. The existing `WordTranslationService` uses instance caching by config signature.

**Suggested Fix:** Add instance caching in `AutoCandidatesRequestHandler.ts`, similar to how `TranslationRequestHandler` caches `getLocalWordService()`.

### P2-5: MIN_BLOCK_TEXT_LENGTH mismatch with spec

**File:** `src/1_content/services/autoTranslationService.ts`

**Problem:** Implementation uses `MIN_BLOCK_TEXT_LENGTH = 30`. The frontend tech spec defines it as `20`.

**Action:** Either update the code to `20` or update the spec to `30` with rationale. (30 is arguably more reasonable as a minimum for meaningful auto-translation.)

---

### P2-6: Over-engineered error handling for silent-failure path

**File:** `src/6_translate/services/AutoCandidatesService.ts`

**Problem:** The `handleAPIError` function has full i18n error mapping (rate limits, business errors, server alerts) identical to the manual translation path. But auto-translation errors are caught silently in `autoTranslationService.ts`.

**Suggested Fix:** Simplify to a generic error throw for V1. Re-add detailed mapping if the service is later used in a user-facing context.

---

### P2-7: `buildExcludedTexts` uses `range.toString()` which is fragile

**File:** `src/1_content/services/autoTranslationService.ts`

**Problem:** `range.toString()` on active translation ranges may return stale/different text if the DOM has been mutated (SPA partial updates). The spec intended using `getActiveTranslationEntry(id).originalText` but no such API exists publicly.

**Suggested Fix:** Expose a method on `translationDisplayV2` to retrieve `originalText` by translation ID, or accept the limitation with a code comment.

---

### P2-8: API types use indexed access pattern

**File:** `src/6_translate/types/AutoCandidatesTypes.ts`

**Problem:** Fields are defined as `fieldName: AutoCandidatesRequestData["fieldName"]` — creating tight coupling to message-layer types. The existing `TranslationApiTypes.ts` defines API types independently.

**Suggested Fix:** Simplify to `export type AutoCandidatesApiRequest = AutoCandidatesRequestData` or define independently.

## Minor Issues (P3 — Nice to Have)

### P3-9: Named import for `createLogger`
`AutoCandidatesService.ts` uses `import { createLogger }` instead of namespace import. Pre-existing inconsistency in the codebase — not a regression.

### P3-10: Redundant `blockElement.contains(node)` checks
`blockTextExtractor.ts` checks `blockElement.contains(node)` twice. TreeWalker is already scoped. Harmless defense-in-depth.

### P3-11: No explicit timeout for auto-candidates request
Relies on underlying `APIService`/`OpenAICompatibleClient` timeouts. Acceptable for fire-and-forget, but a long-pending promise could accumulate memory.

### P3-12: `sendMessageWithRetry` retries 2 times for auto-candidates
For a supplementary fire-and-forget feature, retries add latency on failure. Consider 0 or 1 retry.
