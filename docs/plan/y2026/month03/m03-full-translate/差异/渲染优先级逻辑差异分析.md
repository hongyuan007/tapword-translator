# read-frog vs tapword-translator：DOM 插入与 flex 判断逻辑差异分析

**Date**: 2026-03-17
**Scope**: DOM Renderer (`src/11_full_translate/dom/renderer.ts` vs `read-frog/src/utils/host/translate/dom/translation-insertion.ts`)
**Context**: 针对 P0 级 Bug (Nested Paragraphs / Flex Parent Detection) 修复后引入的排版差异

## 1. 问题背景

`tapword-translator` 全文翻译模块在移植 `read-frog` 的 DOM 渲染逻辑时，为了修复 P0 级 Bug (P0-1, P0-2, P0-3：关于混合块级与内联元素的段落解析以及 Flex 容器保护)，对核心的插入判定函数做了一些调整。

虽然整体上也是遵循 `Walk → Observe → Batch → Render` 架构，并且保留了对 flex 布局的降级保护，但**由于重构了 `insertTranslation` 的签名并去掉了独立的 `isForceInlineTranslation` 函数，导致目前 TapWord 的 `shouldUseInlineInsertion` 逻辑与 Read Frog 原版在“多条件优先级判定”上出现了细微但关键的偏差**。

这可能导致在 Twitter 等深度依赖 Flex 布局的现代 Web 应用中，原本应该“安全内联”的文本被错误换行，或者期望换行的文本被强行内联。

## 2. 代码对比与差异说明

### 2.1 Read Frog 原版实现

**文件**: `read-frog/src/utils/host/translate/dom/translation-insertion.ts`

Read Frog 的设计是严格的**五级优先级链（Priority Chain）**。它将“目标节点自身是否 flex”提取为一个独立的判定函数：

```typescript
// 1. 独立函数：判断目标节点是否强制内联（标签白名单 或 自身是 flex 容器）
export function isForceInlineTranslation(targetNode: TransNode): boolean {
  if (isHTMLElement(targetNode)) {
    const computedStyle = window.getComputedStyle(targetNode)
    return FORCE_INLINE_TRANSLATION_TAGS.has(targetNode.tagName)
      || computedStyle.display.includes("flex")
  }
  return false
}

// 2. 插入逻辑：严格的 if-else 优先级链
export async function insertTranslatedNodeIntoWrapper(..., forceBlockTranslation: boolean = false) {
  const forceInlineTranslation = isForceInlineTranslation(targetNode)
  const customForceBlock = isHTMLElement(targetNode) && isCustomForceBlockTranslation(targetNode)

  // Priority: customForceBlock > forceInlineTranslation > forceBlockTranslation > isInlineTransNode > isBlockTransNode
  if (customForceBlock) {
    addBlockTranslation(...) // 1. 站点自定义强制块级（最高优）
  }
  else if (forceInlineTranslation) {
    addInlineTranslation(...) // 2. 强制内联（标签或自身是 flex）
  }
  else if (forceBlockTranslation) {
    addBlockTranslation(...) // 3. 强制块级（由上游传来：父级是非 flex 的混合段落）
  }
  else if (isInlineTransNode(targetNode)) {
    addInlineTranslation(...) // 4. Walker 标记为内联
  }
  else if (isBlockTransNode(targetNode)) {
    addBlockTranslation(...) // 5. Walker 标记为块级
  }
}
```

### 2.2 TapWord 当前实现 (修复 P0 Bug 后)

**文件**: `tapword-translator/src/11_full_translate/dom/renderer.ts`

在 TapWord 中，`isForceInlineTranslation` 的逻辑被揉进了 `shouldUseInlineInsertion` 里，而且 `forceBlockTranslation` 这个来自上游的参数（表示父级是混合块级段落）被提到了最外层拦截，**打乱了原有的优先级顺序**。

```typescript
// TapWord 的综合判定逻辑
export function insertTranslation(
    paragraphElement: HTMLElement,
    translatedText: string,
    mode: FullTranslateMode,
    options?: InsertTranslationOptions, // 包含 forceBlockTranslation
    metadata?: TranslationWrapperMetadata,
): void {
    // 差异 1：forceBlockTranslation 拥有了最高优先级（一票否决），越过了 customForceBlock 和 forceInline
    const useInline = options?.forceBlockTranslation === true
        ? false  // forceBlock overrides → use block
        : shouldUseInlineInsertion(paragraphElement);
    
    // ... 插入操作
}

// 差异 2：判定逻辑扁平化，优先级顺序改变
function shouldUseInlineInsertion(element: HTMLElement): boolean {
    if (FORCE_INLINE_TRANSLATION_TAGS.has(element.tagName)) return true; // 1. 标签强制内联
    if (isCustomForceBlockTranslation(element)) return false;            // 2. 站点强制块级
    if (element.hasAttribute(INLINE_ATTRIBUTE)) return true;             // 3. Walker 标记内联
    if (element.hasAttribute(BLOCK_ATTRIBUTE)) return false;             // 4. Walker 标记块级

    // 5. 兜底：计算 display (包含了 flex 判定)
    const display = window.getComputedStyle(element).display;
    return display.startsWith('inline') || display.includes('flex');
}
```

## 3. 差异产生的影响 (Impact)

### 影响一：Flex 容器的内联保护失效 (The Twitter Issue)

在 Read Frog 中，如果一个元素是 `<div style="display: flex">`：
- 它会命中 `forceInlineTranslation`（优先级 2），直接采用**内联插入**。
- 即使上游（TranslationWalker）因为它是混合段落传来了 `forceBlockTranslation = true`（优先级 3），也会被优先级 2 拦截，依然安全地内联显示，不会破坏 flex 布局。

在 TapWord 中，如果上游传来了 `options.forceBlockTranslation = true`：
- 在 `insertTranslation` 的第一行，`useInline` 直接被赋值为 `false`。
- 它**根本不会去执行** `shouldUseInlineInsertion`（也就不会执行底部的 `display.includes('flex')` 检查）。
- 结果：一个 Flex 容器内部被强行插入了块级元素（`<br>`），导致原本并排的布局（如推特正文和转推按钮）瞬间错位。

### 影响二：站点级补丁 (`CUSTOM_FORCE_BLOCK_SELECTORS`) 优先级降低

在 Read Frog 中，`customForceBlock` 具有最高优先级（优先级 1）。只要匹配了配置（比如 GitHub 的 `task-lists`），不管三七二十一必须换行。

在 TapWord 中，如果一个元素刚好是 `<button>`（在 `FORCE_INLINE_TRANSLATION_TAGS` 列表里）：
- `shouldUseInlineInsertion` 第一行就会返回 `true`。
- 它永远走不到第二行的 `isCustomForceBlockTranslation` 检查。
- 结果：如果您将来想通过配置强制某个按钮换行翻译，配置将永远失效。

## 4. 修复建议 (Action Item)

建议完全还原 Read Frog 的五级优先级判定链。

在 `src/11_full_translate/dom/renderer.ts` 中重构 `useInline` 的布尔值生成逻辑，使其与 Read Frog 完全一致：

```typescript
// 1. 抽离判定函数，保持职责单一
function isForceInlineTranslation(element: HTMLElement): boolean {
    const display = window.getComputedStyle(element).display;
    return FORCE_INLINE_TRANSLATION_TAGS.has(element.tagName) || display.includes('flex');
}

// 2. 在 insertTranslation 中重构五级优先级链
export function insertTranslation(
    paragraphElement: HTMLElement,
    translatedText: string,
    mode: FullTranslateMode,
    options?: InsertTranslationOptions,
    metadata?: TranslationWrapperMetadata,
): void {
    if (!options?.insertAfterNode && hasTranslatedWrapper(paragraphElement)) return;

    // 目标节点：如果是 unit 级别插入，判定对象是最后一个内联节点；否则是整个段落容器
    const targetNode = (options?.insertAfterNode as HTMLElement) || paragraphElement;

    // 重新实现 Read Frog 的严格优先级链：
    let useInline: boolean;
    
    const customForceBlock = isCustomForceBlockTranslation(targetNode);
    const forceInline = isForceInlineTranslation(targetNode);
    const forceBlockPassedFromUpstream = options?.forceBlockTranslation === true;

    // Priority 1: customForceBlock > Priority 2: forceInline > Priority 3: forceBlock (upstream) > Priority 4/5: Walk attributes
    if (customForceBlock) {
        useInline = false;
    } else if (forceInline) {
        useInline = true;
    } else if (forceBlockPassedFromUpstream) {
        useInline = false;
    } else if (targetNode.hasAttribute(INLINE_ATTRIBUTE)) {
        useInline = true;
    } else if (targetNode.hasAttribute(BLOCK_ATTRIBUTE)) {
        useInline = false;
    } else {
        // Fallback for unlabeled elements (should be rare)
        const display = window.getComputedStyle(targetNode).display;
        useInline = display.startsWith('inline');
    }

    // ... 剩余组装与插入逻辑保持不变
}
```

通过这次重构，TapWord 将完美兼顾之前的 P0 Bug 修复成果，并找回 Read Frog 极其强悍的 Flex 布局保护和动态排版能力。
