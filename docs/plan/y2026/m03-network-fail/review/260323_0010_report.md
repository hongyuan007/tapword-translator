## 🛡️ Review Summary

本次变更在 `TranslationService` 中为云翻译 API 调用添加了 15 秒超时，并在 `handleAPIError` 中将 `timeout`、`requestError`（4xx/无状态码）、`unexpectedError` 三类错误映射为网络级错误消息，与原有服务端错误（`businessError`、`serverAlert`）明确区分。同时新增 4 个 i18n key，覆盖 8 种语言。

**架构评估**: 变更与现有 APIService 的超时机制（AbortController + `RequestOptions.timeout`）完美集成。APIService 已有 `shouldFallback` 逻辑处理 timeout 触发自动切换备用 URL，新增的 `handleAPIError` 的 `case "timeout"` 分支在 fallback 也失败后生效，层级清晰，不冲突。

**整体评价**: 代码质量良好，变更范围精准，i18n 覆盖完整。无严重安全问题。有少量可改进项。

## 🧠 ARCHITECTURAL & LOGIC INSIGHTS

### [设计模式] handleAPIError 分支覆盖完整 ✅
- `handleAPIError` 对 `APIError` 的所有 `type` 枚举值都有对应处理分支：`rateLimited`、`businessError`（含多个 code 分支）、`serverAlert`、`timeout`、`requestError`、`unexpectedError` + `default`。
- 新增的三个分支（`timeout`、`requestError` 的 4xx 分支、`unexpectedError`）逻辑清晰：网络问题归网络，服务问题归服务。

### [弹性] Timeout + Fallback 的交互 ✅
- APIService 的 `shouldFallback()` 已包含 `error.type === "timeout"`，意味着 timeout 会先触发 fallback 尝试，只有 fallback 也失败后才会抛到 `TranslationService.handleAPIError`。这是正确的行为——用户不会因为一次超时就看到错误，系统会先尝试备用服务器。

### [边界情况] requestError 的 code 判断逻辑
```typescript
case "requestError":
    if (error.code && error.code >= 500) {
        // 5xx = server-side issue
        throw new TranslationError(...)
    }
    // 4xx or no code = likely network/proxy issue
    throw new TranslationError(...)
```
- ⚠️ **需要注意**: `error.code` 在 `requestError` 类型下可能为 HTTP 状态码（如 401、403），也可能是 undefined。当前逻辑将所有 4xx 归为网络错误，这在大多数场景下是合理的（因为 401/403/429 已在 APIService 中被分类为 `tokenExpired`/`rateLimited` 专门处理）。但从防御性编程角度看，如果有新的 4xx 状态码未在 APIService 中特别处理，会被归为"网络错误"，语义上不够精确。

### [i18n] Locale 键覆盖一致性 ✅
- 所有 8 个 locale 文件（en/zh/de/es/fr/ja/ko/ru）均包含 4 个新 key，无遗漏。
- Key 命名遵循现有 `error.xxx` / `error.short.xxx` 模式。

### Nice to Have (3)

#### NH-1: `requestError` 中 4xx 与网络错误的区分可更精细
**文件**: `src/6_translate/services/TranslationService.ts`  
**位置**: `handleAPIError` → `case "requestError"`  
**描述**: 当前将所有非 5xx 的 `requestError` 统一映射为"网络错误"，但理论上可能出现 4xx（如 400 Bad Request）被误归类为网络问题的情况。  
**建议**: 可考虑增加一个注释说明哪些 4xx 已被 APIService 拦截（401→tokenExpired, 429→rateLimited），剩余到达此处的 4xx 确实大概率是网络/代理问题。或在 `requestError` case 中单独处理 400-408（客户端错误），将 409-499 归为网络错误。  
**影响**: 低。当前 APIService 已拦截主要 4xx，实际到达此处的概率极低。

#### NH-2: `TRANSLATION_REQUEST_TIMEOUT_MS` 可考虑提取为可配置常量
**文件**: `src/6_translate/services/TranslationService.ts`  
**位置**: 第 30 行  
**描述**: 15 秒超时硬编码为模块级常量。未来如果需要根据网络环境（如中国区 vs 国际区）调整超时时间，需要修改代码。  
**建议**: 可考虑放入 `TranslationConstants.ts` 或与 `UserSettings` 联动（但增加复杂度，短期不建议）。当前作为常量是合理的。  
**影响**: 极低。

#### NH-3: MTranServer / Bing Translate 调用未添加超时
**文件**: `src/6_translate/services/TranslationService.ts`  
**位置**: `translateWord` / `translateFragment` 函数中 MTranServer 和 Bing Translate 分支  
**描述**: 本次变更为官方云 API 添加了 15s 超时，但 MTranServer 和 Bing Translate 的调用未做相同处理。如果用户使用这些 provider，长时间无响应时没有超时保护。  
**建议**: 评估是否需要为 MTranServer/Bing 的请求也添加超时（取决于各自 Service 内部是否已有超时机制）。如果它们内部已有，则无需重复；如果没有，可在后续迭代中补齐。  
**影响**: 中。取决于各 Service 内部实现。
